`ASOF` joins, SQL registration of external catalogs, Avro and ALP write support,
better support for extension types, and many performance and stability improvements. The complete list of
changes is available in the [changelog]. This release represents roughly 12
weeks of development and 1200 commits. Thanks to the [247 contributors].

## New Features ✨

### `ASOF` Joins

DataFusion 56 adds `ASOF JOIN`, a long-standing feature request ([#318]) 
that matches each row on the left with the
*closest* row on the right rather than an exact match. Such joins are
common in time-series workloads such as finding the most recent quote for each
trade, or aligning two sensors that sample at different rates.

For example, given tables of `temperature` and `humidity` readings from two
sensors that report at different times:

| id | location | ts                  | temp |
|----|----------|---------------------|------|
| T1 | roof     | 2026-11-20T09:30:05 | 11.5 |
| T2 | roof     | 2026-11-20T09:30:12 | 11.7 |
| T3 | lobby    | 2026-11-20T09:30:07 | 20.1 |

| id | location | ts                  | humidity |
|----|----------|---------------------|----------|
| H1 | roof     | 2026-11-20T09:30:00 | 71.0     |
| H2 | roof     | 2026-11-20T09:30:10 | 70.5     |
| H3 | lobby    | 2026-11-20T09:30:10 | 45.2     |

Since no temperature reading has the exact same timestamp as any humidity
reading, a regular equality join on `location` and `ts` would match nothing.
Instead, an `ASOF` join efficiently pairs each temperature reading with the most
recent humidity reading at or before it:

```sql
SELECT t.id AS temp_id, h.id AS humidity_id, t.location, t.ts, t.temp, h.humidity
FROM temperature AS t ASOF JOIN humidity AS h
MATCH_CONDITION (t.ts >= h.ts)
ON t.location = h.location
ORDER BY t.id;
```

```text
+---------+-------------+----------+---------------------+------+----------+
| temp_id | humidity_id | location | ts                  | temp | humidity |
+---------+-------------+----------+---------------------+------+----------+
| T1      | H1          | roof     | 2026-11-20T09:30:05 | 11.5 | 71.0     |
| T2      | H2          | roof     | 2026-11-20T09:30:12 | 11.7 | 70.5     |
| T3      | NULL        | lobby    | 2026-11-20T09:30:07 | 20.1 | NULL     |
+---------+-------------+----------+---------------------+------+----------+
```

<details>
<summary>Full Example</summary>

```sql
CREATE TABLE temperature (id VARCHAR, location VARCHAR, ts TIMESTAMP, temp DOUBLE) AS VALUES
  ('T1', 'roof',  '2026-11-20T09:30:05', 11.5),
  ('T2', 'roof',  '2026-11-20T09:30:12', 11.7),
  ('T3', 'lobby', '2026-11-20T09:30:07', 20.1);

CREATE TABLE humidity (id VARCHAR, location VARCHAR, ts TIMESTAMP, humidity DOUBLE) AS VALUES
  ('H1', 'roof',  '2026-11-20T09:30:00', 71.0),
  ('H2', 'roof',  '2026-11-20T09:30:10', 70.5),
  ('H3', 'lobby', '2026-11-20T09:30:10', 45.2);

MATCH_CONDITION (t.ts >= h.ts)
```

See the [`ASOF JOIN` documentation][ASOF JOIN documentation] for more details.

### External Catalogs in SQL

Connecting DataFusion to an external catalog, such as an Iceberg REST catalog,
previously required writing Rust code. DataFusion 56 adds
`CREATE EXTERNAL CATALOG` and `DROP CATALOG` statements ([#25112]), so catalogs
can be attached with SQL in the same way as external tables:

```sql
CREATE EXTERNAL CATALOG my_catalog
STORED AS ICEBERG
LOCATION 's3://bucket/warehouse'
OPTIONS ('catalog.uri' 'http://rest-catalog:8181', 'warehouse' 'my_catalog');

SELECT * FROM my_catalog.sales.orders LIMIT 10;
```

DataFusion does not include catalog implementations itself. Instead, libraries
such as table format integrations register a [`CatalogProviderFactory`][CatalogProviderFactory] for
each `STORED AS` type, and users can then attach catalogs without any
additional code; see the [`CREATE EXTERNAL CATALOG` documentation][CREATE EXTERNAL CATALOG documentation] for details.

To make working with multiple catalogs more practical, `information_schema`
queries are now scoped to a single catalog, as the SQL standard specifies
([#25887]): `my_catalog.information_schema.tables` lists only the tables in
`my_catalog`, and an unqualified `information_schema` refers to the default
catalog.

Thanks to [@pepijnve] and [@TTyChud] for this work.

[CatalogProviderFactory]: https://docs.rs/datafusion/56.0.0/datafusion/catalog/trait.CatalogProviderFactory.html
[CREATE EXTERNAL CATALOG documentation]: https://datafusion.apache.org/user-guide/sql/ddl.html#create-external-catalog

### File Format Improvements

**Writing Avro**: DataFusion has been able to read [Apache Avro] files for a
long time, and DataFusion 56 adds support for writing them:

```sql
CREATE TABLE orders (id INT, customer VARCHAR, total DOUBLE) AS VALUES
  (1, 'alice', 42.50),
  (2, 'bob', 17.25),
  (3, 'carol', 99.99);

-- Write the table to an Avro file
COPY orders TO 'orders.avro' STORED AS AVRO;

-- Read it back
SELECT * FROM 'orders.avro';
+----+----------+-------+
| id | customer | total |
+----+----------+-------+
| 1  | alice    | 42.5  |
| 2  | bob      | 17.25 |
| 3  | carol    | 99.99 |
+----+----------+-------+
```

**Parquet ALP Encoding**: [ALP] (Adaptive Lossless floating-Point) is a new
Parquet encoding that often stores `FLOAT` and `DOUBLE` columns much more
compactly. DataFusion 56 can read and write ALP-encoded files. To write a
column using ALP, select the encoding and turn off dictionary encoding for that
column (dictionary encoding otherwise takes precedence):

```sql
COPY measurements TO 'measurements.parquet' STORED AS PARQUET
OPTIONS (
  'format.encoding::price' 'alp',
  'format.dictionary_enabled::price' 'false'
);
```

<details>
<summary>Full Example</summary>

```sql
-- One million prices with two decimal places
CREATE TABLE measurements AS
SELECT i AS id, round(100000 * random(), 2) AS price
FROM generate_series(1, 1000000) AS t(i);

-- Write with the default settings, and with ALP for the price column
COPY measurements TO 'alp.parquet' STORED AS PARQUET
OPTIONS (
  'format.encoding::price' 'alp',
  'format.dictionary_enabled::price' 'false'
);

-- Compare the size of the price column in the two files
SELECT 'alp', encodings, total_compressed_size
FROM parquet_metadata('alp.parquet') WHERE path_in_schema = '"price"';
+---------+------------------------------+-----------------------+
| file    | encodings                    | total_compressed_size |
+---------+------------------------------+-----------------------+
| default | [PLAIN, RLE, RLE_DICTIONARY] | 4481181               |
| alp     | [RLE, ALP]                   | 3018657               |
+---------+------------------------------+-----------------------+
```

</details>

In this example the ALP-encoded column is about a third smaller than with the
default settings. ALP is a recent addition to Parquet, so check that the other
systems that read your files support it before using it.

### More SQL Support

**`MATERIALIZED` CTEs**: By default, DataFusion inlines Common Table
Expressions (CTEs), so a CTE that is referenced several times is evaluated
several times. DataFusion 56 supports the Postgres
`WITH ... AS [NOT] MATERIALIZED` syntax to evaluate a CTE once and reuse the
result ([#25580]):

```sql
WITH r AS MATERIALIZED (SELECT random() AS v)
SELECT a.v = b.v FROM r a, r b;
-- true: the CTE runs once and both references see the same value
```

Thanks to [@adriangb] for this work.

### Improved support for Extension Types

As described in [the User Defined Types blog], DataFusion allows users to extend
the types using [Arrow extension types] to attach a logical type to a standard
arrow physical type. Extension types permit the DataFusion ecosystem to add
entirely new data types *without* changes to the DataFusion core (see
[Ecosystem Highlights] below). DataFusion 56 improves this support in several ways:

- The SQL types `UUID` and `JSON` now map to
  the Arrow [canonical extension types] `arrow.uuid` and `arrow.json`.
- `DESCRIBE`, `SHOW COLUMNS`, and
  `information_schema.columns` show the extension type name rather than the
  storage type.
- Extension types are preserved when reading Parquet
  files with the default settings.
- Extension types are preserved through more operators such as
  casts, `min` / `max`, scalar subqueries, and `INSERT`.

For example, a column declared with the SQL `JSON` type is stored as a standard
Arrow string and tagged with the `arrow.json` extension type:

```sql
CREATE TABLE events (doc JSON);
INSERT INTO events VALUES ('{"a":1}');
SELECT doc,
       arrow_typeof(doc)                           AS doc_type,
       arrow_metadata(doc)['ARROW:extension:name'] AS doc_extension
FROM events;
+---------+----------+---------------+
| doc     | doc_type | doc_extension |
+---------+----------+---------------+
| {"a":1} | Utf8     | arrow.json    |
+---------+----------+---------------+
```

Thanks to [@cblp], [@cyberbeam524], [@paleolimbot], [@M-Tesla], and
[@osipovartem] for this work.

[Arrow extension types]: https://arrow.apache.org/docs/format/Columnar.html#extension-types
[canonical extension types]: https://arrow.apache.org/docs/format/CanonicalExtensions.html
[Ecosystem Highlights]: #ecosystem-highlights
[the User Defined Types blog]: https://datafusion.apache.org/blog/2025/09/21/custom-types-using-metadata

## Ecosystem Highlights 🌱

DataFusion is designed to be extended, and some of the most exciting new
features are built by the community on top of it rather than added to the
core. This section highlights two such projects.

### Semi-Structured Data (e.g. JSON)

Parquet [Variant] is a type for storing semi-structured data, similar to JSON
with an efficient binary encoding and is part of Apache Parquet and Apache
Iceberg (see the [blog on the Parquet site] for background).  The
[datafusion-variant] crate extends DataFusion via its extension APIs to add the
`VARIANT` SQL type and Spark-compatible functions. Register it on a
`SessionContext`:

```rust
let mut ctx = SessionContext::new();
datafusion_variant::register_all(&mut ctx)?;
```

Then you can load, query, and store semi-structured data using SQL:

```sql
-- Load JSON data into a VARIANT column
CREATE TABLE events AS
SELECT parse_json(json_data) AS event
FROM (VALUES
    ('{"service":"api","status":200,"latency_ms":12,"tags":["cached"]}'),
    ('{"service":"api","status":500,"latency_ms":85,"error":null}'),
    ('{"service":"api","status":504,"error":"Somethings not working"}')
) AS input(json_data);

-- Extract fields with the Spark-style `:` operator
SELECT event:service::VARCHAR,
       event:latency_ms::BIGINT
FROM events
WHERE event:status::BIGINT >= 400;
```

```text
+----------------------+-------------------------+
| events.event:service | events.event:latency_ms |
+----------------------+-------------------------+
| api                  | 85                      |
| api                  | NULL                    |
+----------------------+-------------------------+
```

Variant columns can be written to Parquet files with `COPY`  statements,
including optionally [*shredding* commonly used fields][Variant shredding] into typed Parquet columns
for faster queries:

```sql
COPY events TO 'shredded_events.parquet' STORED AS PARQUET
OPTIONS ('variant.shredding' '{"event": "STRUCT<service VARCHAR, status BIGINT>"}');
```

The `datafusion-variant` crate is under active development, refer to the project
documentation for more details.

[geodatafusion] provides spatial extensions for DataFusion, built on the
[GeoArrow] extension types and modeled after the [PostGIS] SQL API. It includes
around 90 spatial functions such as [`ST_Distance`][ST_Distance] and [`ST_Intersects`][ST_Intersects], support
for reading [GeoParquet], reading and writing [FlatGeobuf], and writing GeoJSON
files, and Python bindings.

As with Variant, a single call registers the spatial functions:

```rust
let ctx = SessionContext::new();
geodatafusion::register(&ctx);
```

and geometries can then be queried using familiar PostGIS-style SQL:

```sql
SELECT ST_Distance(ST_Point(0, 0), ST_Point(3, 4)) AS dist;

SELECT ST_Area(ST_GeomFromText('POLYGON((0 0, 4 0, 4 4, 0 4, 0 0))'));
```

Together, `datafusion-variant` and `geodatafusion` illustrate what the extension
type work makes possible: sophisticated new data types, with their own SQL
syntax, functions, and file format integrations, built and released
independently by the community. If you need a type that DataFusion does not
have, you can now build it.

### Faster Builds

Building the `datafusion` crate and its dependencies from scratch is now about
3x faster end to end, and some individual crates, including the core
`datafusion` crate, compile up to 10x faster ([#24329], [#24325], [#24330],
[#24326]). Thanks to [@Dandandan].

### Faster TopK and `LIMIT` Queries

Queries that return only a few rows keep getting faster. DataFusion 56 can
evaluate `ORDER BY ... LIMIT` *before* an outer join when the sort columns come
from the preserved side, so far fewer rows are joined ([#21621]). For example,
this query now joins only three orders rather than every order:

```sql
SELECT o.id, o.total, c.name
FROM orders AS o LEFT JOIN customers AS c ON o.customer_id = c.id
ORDER BY o.total DESC
LIMIT 3;
```

Parquet scans now stop after reading only the *pages* that are
guaranteed to satisfy a `LIMIT` query's filter ([#25000]), and custom table
providers can implement `OFFSET` pushdown, which is useful for paging through
results ([#25404]). Thanks to [@SubhamSinghal], [@peterxcli], and [@martin-g].

### Faster Joins

Dynamic filters created by a join are now applied to *other* tables that are
joined on the same key, and pushed through nested loop joins, skipping more
data at the scan ([#25255], [#25030]). Other join improvements include faster
sort-merge joins ([#26277]), a nested loop join that needs half the memory
([#25371]), faster range joins ([#24579]), and rewriting joins against a single
constant row into filters ([#26404]). Thanks to [@jayzhan211], [@yashrb24],
[@andygrove], [@2010YOUY01], and [@xudong963].

### Faster Aggregations and Subqueries

Aggregations over already sorted inputs now avoid hashing entirely
([#25150], [#26370]), and ordered `ARRAY_AGG` and `STRING_AGG` are over 10x
faster while using less than half the memory ([#24392]). `IN` and `NOT IN`
subqueries used as expressions (for example in the `SELECT` list) are now
planned as a single join, which makes some queries hundreds of times faster
([#25338]). Thanks to [@QinXi-ai], [@geoffreyclaude], [@lyne7-sc],
[@zhuqi-lucas], and [@adriangb].

### Faster Functions and Expressions

As in previous releases, many functions are faster, including `upper`, `lower`,
`translate`, `replace`, `left`, `right`, `levenshtein`, along with `IN` list
evaluation. Thanks to [@neilconway], [@geoffreyclaude], [@andygrove],
[@Rich-T-kid], and [@comphead] for making this happen. 

## Stability Improvements 🛡️

**Correctness**: As a foundational piece of technology, it is important that
DataFusion's results can be relied on. During this release cycle the community
systematically focused on finding and fixing bugs that produced incorrect
results. The tracking epic ([#26672]) lists more than 60 such bugs that are
fixed in DataFusion 56, along with the ones we are still working on. Thanks to
[@haohuaijin], [@adriangb], [@AdamGS], [@matthewmturner], [@viirya],
[@mbutrovich], and the many others who reported, fixed, and reviewed these
issues.

**More Robust Larger-Than-Memory Queries**: Queries that spill to disk when
memory runs out are more robust. Aggregations with very large groups (such as
`array_agg` over a few keys) no longer fail after spilling ([#25853]), spill
files for string and dictionary data are smaller ([#23565], [#27015]), and
memory accounting is more accurate ([#24744], [#25188], [#26074]). Thanks to
[@andygrove], [@cetra3], [@brancz], and [@kosiew].

## About DataFusion

[Apache DataFusion] is an extensible query engine, written in [Rust], that uses
[Apache Arrow] as its in-memory format. DataFusion is used by developers to
create new, fast, data-centric systems such as databases, dataframe libraries,
and machine learning and streaming applications. While [DataFusion's primary
design goal] is to accelerate the creation of other data-centric systems, it
provides a reasonable experience directly out of the box as a [dataframe
library], [Python library], and [command-line SQL tool].

DataFusion's core thesis is that, as a community, together we can build much
more advanced technology than any of us as individuals or companies could build
alone. Without DataFusion, highly performant vectorized query engines would
remain the domain of a few large companies and world-class research
institutions. With DataFusion, we can all build on top of a shared foundation
and focus on what makes our projects unique.
